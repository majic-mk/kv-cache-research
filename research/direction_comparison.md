# KV-cache direction audit, 2026-10-03

**Ranking superseded:** see `narrow_alternatives.md`. The scheduling candidate failed a simple shared-aware baseline test in the independent evaluation audit. The current provisional main is a small falsification study of cross-region calibration transfer in query-agnostic compression; broad scheduling is rejected.

## Decision

No direction is publication-greenlit. The low-cost **main diagnostic pilot** can test **load-uncertainty-aware exact-prefix restoration**, with **reuse-count-aware investment in query-agnostic compression** as the backup. **The broad main formulation is killed as a novelty claim by MTDS, Strata, Kareto, and current transfer scheduling.** Only a measured failure of those strong baselines could revive a much narrower method. Generic RAG chunk-cache repair should also be rejected as a main contribution: its obvious extensions have already appeared, including in September 2026. This is a provisional diagnostic prioritization, not a positive recommendation to implement a new system or a novelty certificate.

Scope: literature first submitted or published from 2024-10-03 through 2026-10-03, plus explicitly marked earlier foundations. Sources below are primary papers, author repositories, official engine code/docs, or official project design documents. No GPU workloads, installations, paid services, or model downloads were run. Paper speedups are author claims, not reproduced results. Search was broad but not exhaustive.

[TensorRT-LLM's current primary documentation](https://nvidia.github.io/TensorRT-LLM/features/kv-cache-compression.html) also exposes iteration-driven and storage-bound compression, including NVFP4 cold pages, and explicitly co-designs storage, transfer and execution. Calling cache lifecycle integration itself novel is untenable. Its moving documentation must be mapped to a fixed release for any implementation comparison.

## Three concrete candidates

### 1. Main pilot: exact-prefix restoration under uncertain load and interference

**Question.** With a fixed GPU/CPU/storage budget, does treating retrieval time as a load-dependent distribution rather than one static bandwidth number materially improve exact-prefix request SLO attainment? The decision is per pending prefix: wait for an in-flight shared producer, retrieve from host/storage, or recompute. A cached byte is useful only when it can be made ready before its consumer, without causing worse decode interference elsewhere.

**Proposed narrow contribution, conditional on evidence.** A measured, uncertainty-aware completion-time policy with explicit shared-prefix dependency accounting and a bounded interference budget. This must be distinguishable from MTDS’s historical-latency route selection, Strata’s batching, Kareto’s adaptive tuning, and current HiCache policies; the intended remaining hypothesis is a failure under nonstationary competing resource demand that cannot be fixed by ordinary tuning. A tail percentile alone is not substantive novelty. Novelty confidence: low. Engineering feasibility: high relative to the alternatives. Status: diagnostics only; do not start a new scheduler implementation without the headroom gate.

**Low-cost falsification before engine changes.** Use a single already-available 3B model, then one 7–8B model, BF16 weights. Collect a small matrix of exact prefill, host restore, and optional local-disk restore at 2K/8K/16K prefixes while another stream decodes. Record queue wait, storage wait, transfer, gather/scatter, GPU interference, and first-token time separately. On measured traces, compare the best fixed crossover, current HiCache wait policies, an online point-estimate policy, the proposed upper-quantile policy, and a clairvoyant route oracle. Freeze calibration separately from held-out replay. The CPU-only trace phase can precede a small instrumented replay; simulation alone cannot establish a systems result.

**Strong baselines.** Full recompute; exact GPU-only prefix cache; SGLang HiCache with best-effort/wait-complete/timeout each tuned equally; Strata-style balanced batches and delay-hit handling; MTDS-style observed-latency full/partial/no-load selection; tuned static cost crossover; simple moving-average cost model; upper-bound oracle. LMCache gives an independent engine/cache implementation. KVPR is an algorithmic prior, not a directly fair out-of-box modern-serving baseline. Include no-interference and no-cache-reuse controls. Kareto is an additional required comparison if the contribution changes tier sizes or eviction.

**Stop gates.**
0. Before GPU measurement, formalize shared-prefix restoration jobs with conflicting per-request deadlines and coupled GPU/PCIe resource reservations. Construct a *minimal counterexample* against both MTDS-style independent route choice and Strata-style shared-hit batching. A toy advantage from counting the same transfer twice does not pass: coalescing is already known, and Dynamo preserves transfers still needed by other dependents. No such surviving counterexample was established in this survey. If none exists, reject the scheduling direction rather than relabeling an uncertainty margin as a new mechanism.
1. Kill if clairvoyant route choice improves p95 TTFT or SLO goodput by <15% over the best equally tuned fixed policy on two held-out, materially different traces. There is too little route-choice headroom.
2. Kill if gains are only an upstream bug fixed in the pinned current baseline. For example [HiCache issue 32724](https://github.com/sgl-project/sglang/issues/32724) already documents delayed completion visibility and proposes decoupled finalization. Do not sell that known fix as research.
3. Kill if the dynamic policy adds >5% overhead in the uncontended control, starves cold prefixes, or merely trades unacceptable TPOT for TTFT.
4. Kill/merge into prior work if current HiCache/Strata/Dynamo already implements the same decision rule after code-level audit.
5. Pass only if end-to-end replay shows >=15% SLO goodput or p95 improvement over every deployable tuned baseline in at least two meaningful regimes, with no correctness change and small steady-state regression. These are project go/no-go targets, not claimed results or publication guarantees.

**Risks.** Single-machine policy may be an engineering patch; artificial throttling can manufacture gains. Real PCIe/CPU/SSD behavior and actual trace diversity are essential. GPU 5090 support and deterministic output need testing. Exact cache semantics do not automatically imply bitwise identical outputs if batching changes floating-point kernels; check logits within a predeclared tolerance, greedy tokens, and near-tie exceptions under deterministic settings.

### 2. Backup pilot: when to invest in reusable cache compression

**Question.** For contexts with unknown future reuse counts, when should a server pay expensive query-agnostic cache construction or reconstruction rather than keep a cheap representation? Compare cheap first-use compression, expensive immediate compression, deferred upgrade after measured reuse, and no compression, under a fixed *total* memory budget.

**Proposed gap.** The investment policy, not a new token score: account for construction, data loading, upgrade, cache replacement, and all future queries. KVzip motivates reusable caches; KVzap, FastKVzip and EchoPress make construction cheaper. The open empirical question is whether those improvements leave enough heterogeneous lifetime cost for adaptive investment to matter. This pass did not verify a directly matching author implementation of the investment policy. Absence from this search does not prove novelty.

**Low-cost falsification.** First measure per-document construction time, actual stored bytes, peak allocation, and 1/2/4/8/16-query total wall time on 8K and 16K contexts. Use a held-out set with both short-lived and repeatedly queried documents; no query is visible to the reusable compressor. Evaluate KVzip, KVzap/FastKVzip, EchoPress where verified, ExpectedAttention, and full cache. Simulate finite CPU/GPU capacity and return-time distributions from these measurements, then replay only if a nontrivial crossover exists. Upgrade must reconstruct from original tokens/full source state; it cannot recover evicted data for free. Include that state in memory and I/O accounting.

**Baselines.** Best global static compressor/retention chosen on validation; best length-bucketed static choice; fixed reuse-count thresholds; never upgrade; always expensive; oracle known lifetime; FP8 or 4-bit full-token cache. Include start+recent, random, and KeyDiff pruning controls. VarRate is relevant if available and reproducible. Compare quality at matched real bytes, not only retained-token ratios.

**Stop gates.** Kill if EchoPress/KVzap is within 5% total cost and 1 absolute quality point of the expensive method across the tested reuse range, or if the oracle investment policy offers <15% lifetime improvement over the best static policy. Kill if extra source-state storage removes the memory benefit. Kill a method-paper framing if all gains are explained by a standard ski-rental threshold; it would need a substantive new cost/quality interaction or a useful, carefully scoped systems result. Pass only after held-out end-to-end lifetime cost improves while paired quality degradation remains within a declared noninferiority margin.

**Risks.** An easy-to-run HF experiment is not a deployable serving win. Query drift, selection leakage, re-prefill peaks, old attention patches, and complete-query latency versus attention-only timing can reverse results. A single 8B model is feasible; training a new large surrogate is unnecessary for this pilot.

### 3. High-risk alternative: byte-budgeted RAG repair with precision-sensitive selection

**Question.** At fixed CPU storage and transfer bytes, can the system allocate precision and recomputation so that repair selection is not dominated by quantization noise? A narrowly testable hypothesis is that repair token rankings inferred from low-bit cached states differ from BF16 rankings in a way that wastes recompute, and that a tiny high-precision scoring sidecar or corrected score restores a better frontier.

**Why this is currently red.** AgentKVShift already demonstrates residual correction under low-bit cache; C²KV already joins compression with composability; Cache-Craft already adapts repair and variants; RelaxKV selects sparse repair context; CacheRepair learns residual repair. Simply composing a quantizer and repair method, using a small model, or optimizing “storage+quality+latency” is not enough.

**Minimal diagnostic.** On Qwen2.5-3B and later a separate 7–8B model, compute paired full-prefill, BF16 independent-chunk, 8-bit, and 4-bit caches for 100–200 held-out questions. Compare fixed boundary repair, random repair, value-difference repair, query-attention repair, and AgentKVShift where reproducible. Separate causal mismatch from quantization mismatch with exact-prefix quantization controls. Measure target-set overlap, true quality effect, actual bytes including sidecars, and host-to-first-token time. Use natural multihop QA plus controlled stale-role/ordering tests from Boxoffice only after license resolution. A diagnostic “oracle selector” may inspect full references but must never be presented as deployable.

**Stop gates.** Kill if low-bit selection ranking has no causal effect after matched controls; if a simple fixed 8-bit cache or AgentKVShift dominates; if a sidecar’s bytes/transfer erase the gain; or if end-to-end improvement vanishes against an optimized full prefill. This is at most a short falsification pilot until its precise new mechanism survives direct C²KV and AgentKVShift comparison.

## 32-GB feasibility and experimental guardrails

The [RTX 5090 official specification](https://www.nvidia.com/en-us/geforce/graphics-cards/50-series/rtx-5090/) confirms 32 GB GDDR7 and CUDA capability 12.0. Do not confuse compute capability 12.0 with toolkit version 12.0. Modern runtime support must be smoke-tested; old CUDA 12.1 paper recipes are not a portable promise for this GPU.

Use one dense 3B/7–8B model at a time, BF16 weights initially, 8K–16K contexts, short 32–128 token outputs, and batch size one for mechanistic quality before small continuous batches. A nominal 8B BF16 weight payload is about 16 GB before runtime buffers; 14B BF16 is too tight for a default 32-GB research setup. KV memory must be calculated from actual model configuration as 2 × layers × KV heads × head dimension × bytes × tokens, then augmented by repair activations, duplicated caches, scores, pinned host data, and workspaces. Analytical fit is not a measurement.

For every candidate: freeze original prompt token IDs/order, model/tokenizer weights, cache layout, RoPE positions, precision, seed, attention backend and warmup procedure. Record HBM allocated/reserved, host bytes, transfer bytes, all construction and reload costs, p50/p95/p99 TTFT, TPOT, throughput and SLO goodput. Use open-loop arrival replay to avoid coordinated omission. Match bytes and quality, not just nominal compression/recompute ratios. Report cold start, warm cache and total lifetime separately. All claimed correctness/quality differences require paired examples and uncertainty intervals; include full results as well as full-prefill-correct subsets so legitimate improvements are not silently discarded. No top-conference, speedup, or accuracy-preservation claim is warranted before these gates pass.
